## 📖 درباره پروژه

**آنست** یک سیستم مدیریت انبار (WMS) برای مدیریت و ردیابی موجودی در چندین سطح سازمانی است.

سیستم از ساختار سلسله‌مراتبی انبارها پشتیبانی می‌کند و امکان ثبت و کنترل فرآیندهایی مانند:

* ثبت ورود و خروج کالا
* مدیریت موجودی
* انتقال کالا بین انبارها
* تأیید و پیگیری انتقالات
* مدیریت کاربران و سطح دسترسی
* ثبت تاریخچه عملیات
* گزارش‌گیری از وضعیت و گردش کالا

را فراهم می‌کند.

یکی از بخش‌های مهم پروژه، مدیریت صحیح جریان کالا در ساختار **مرکزی → منطقه‌ای → محلی** است. قوانین کسب‌وکار مستقیماً در معماری سیستم و همچنین در سطح دیتابیس enforce شده‌اند تا از ایجاد وضعیت‌های نامعتبر جلوگیری شود.

# 🎯 مسئله‌ای که حل می‌کند

در یک سیستم انبار معمولی، تغییر موجودی می‌تواند به سادگی با تغییر یک فیلد `quantity` انجام شود.

اما در این پروژه، هر تغییر موجودی باید قابل پیگیری باشد و قوانین مشخصی را رعایت کند.

برای مثال:

* یک انبار محلی نباید بتواند بدون مجوز کالا را به سطح بالاتر برگرداند.
* هر انتقال باید مشخص کند چه کسی آن را ایجاد و تأیید کرده است.
* وضعیت انتقال باید مرحله‌به‌مرحله تغییر کند.
* دو درخواست همزمان نباید باعث ثبت موجودی اشتباه شوند.
* اطلاعات تاریخی عملیات نباید با تغییر موجودی از بین برود.

به همین دلیل، پروژه صرفاً به یک CRUD ساده متکی نیست و بخش مهمی از منطق در لایه Domain، Application و Database پیاده‌سازی شده است.

# 🔄 مدیریت موجودی و Event Sourcing

یکی از تصمیم‌های مهم معماری پروژه، استفاده از رویکرد **Event Sourcing** برای ثبت تغییرات موجودی است.

به جای اینکه فقط مقدار فعلی موجودی را ذخیره کنیم، تغییرات مهم نیز به صورت Event ثبت می‌شوند.

برای مثال:

```text
StockIncreased
StockDecreased
TransferCreated
TransferApproved
TransferCompleted
```

در نتیجه می‌توان تاریخچه تغییرات یک موجودی را بررسی کرد و متوجه شد که مقدار فعلی چگونه به وجود آمده است.

برای کنترل حجم Eventها، از Snapshot نیز استفاده شده تا بازسازی وضعیت در حجم بالای داده‌ها کارآمد باقی بماند.

# 🔐 کنترل قوانین کسب‌وکار در Database

بخشی از قوانین مهم سیستم فقط در Backend پیاده‌سازی نشده‌اند.

برای قوانین حساس، PostgreSQL نیز به عنوان یک لایه حفاظتی اضافی استفاده می‌شود.

برای مثال:

* بررسی ساختار سلسله‌مراتبی انبارها
* جلوگیری از انتقال‌های غیرمجاز
* کنترل وضعیت انتقال
* اجرای عملیات حساس در Transaction
* جلوگیری از ثبت وضعیت‌های نامعتبر

این رویکرد باعث می‌شود حتی در صورت وجود خطا در یک لایه، دیتابیس نیز از داده‌ها محافظت کند.

# ⚡ مدیریت همزمانی

یکی از چالش‌های پروژه، درخواست‌های همزمان برای تغییر موجودی یک کالا بود.

برای مثال، اگر دو کاربر به صورت همزمان بخواهند یک کالا را از یک انبار خارج کنند، هر دو درخواست نباید بر اساس یک مقدار قدیمی موجودی تصمیم بگیرند.

برای حل این مسئله، عملیات حساس در سطح PostgreSQL و داخل Transaction کنترل می‌شود و از:

```text
pg_advisory_xact_lock
```

برای ایجاد lock روی ترکیب:

```text
Warehouse + Product
```

استفاده شده است.

در نتیجه درخواست‌های همزمان برای یک منبع مشخص به صورت کنترل‌شده اجرا می‌شوند.

# 👥 احراز هویت و دسترسی

سیستم دارای **RBAC** و کنترل دسترسی مبتنی بر منبع است.

دسترسی کاربران فقط به Role محدود نمی‌شود و در موارد لازم، ارتباط کاربر با انبار مورد نظر نیز بررسی می‌شود.

به عنوان مثال:

```text
Admin
 └── دسترسی گسترده

Warehouse Manager
 └── مدیریت انبارهای مجاز

Warehouse Operator
 └── عملیات محدود روی انبار اختصاص داده‌شده
```

احراز هویت API با **JWT** انجام می‌شود و درخواست‌های غیرمجاز با `401` یا `403` پاسخ داده می‌شوند.

# 📌 نکات مهندسی مهم

چند مورد از چالش‌های اصلی این پروژه:

**1. مدل‌سازی موجودی**

موجودی فقط یک `quantity` ساده نیست و باید تاریخچه تغییرات آن نیز قابل پیگیری باشد.

**2. قوانین انتقال**

جریان انتقال کالا بر اساس ساختار سلسله‌مراتبی سازمان کنترل می‌شود.

**3. Concurrency**

درخواست‌های همزمان برای تغییر یک موجودی باید بدون ایجاد Race Condition مدیریت شوند.

**4. Auditability**

عملیات مهم سیستم باید قابل ردیابی باشند.

**5. Defense in Depth**

قوانین حساس فقط به یک لایه وابسته نیستند و در سطح Application و Database نیز کنترل می‌شوند.
